# 上下文工程

> 本文档目的：介绍上下文工程的概念、范围与核心环节，明确上下文压缩在其中的定位。

## 一、什么是上下文工程

上下文工程（Context Engineering）是系统性地管理 Agent 工作过程中上下文的全流程方法论——从信息产生、注入、压缩、检索到移除的生命周期管理。

核心目标：让 Agent 的上下文保持高信噪比——当前任务直接需要的信息在窗口内，不需要的信息不放入或按需拉取。

## 二、核心环节

### 1. 上下文注入（Injection）

决定什么信息进入窗口，以及什么时候进入。

- 系统提示词、工具定义
- 当前文件 / 选区 / 最近编辑内容
- 用户当前输入
- 项目指令文件（`AGENTS.md`、`CLAUDE.md`、`.cursorrules`）

核心问题：放多了噪音大，放少了 Agent 缺信息。

压缩后需要重新注入稳定上下文（项目规则文件），防止压缩丢失关键约束。

### 2. 工具输出截断（Truncation）

工具结果进入上下文之前即截断，不等压缩触发。

- Codex CLI：记录时即截断，默认 10,000 bytes
- Claude Code：Budget Reduction 层，对每条消息的工具输出设大小上限

和压缩的区别：截断是"进来之前就砍"，压缩是"进来之后满了才缩"。

### 3. 上下文压缩（Compression）

信息超出窗口时缩减。

- 摘要压缩（对话历史 → running summary）
- token 级压缩（实际用得少）
- 任务交接摘要（Codex CLI 的 handoff summary）

### 4. 上下文外置（Offloading）

把大块信息移到外部存储，窗口内只留引用。

- 大工具结果写入文件，窗口内留路径 + 预览（Deep Agents：>20K token 自动外置）
- 聊天历史文件化（Cursor：窗口满后给 agent 历史文件引用）
- MCP 工具描述文件化（Cursor：只塞工具名列表，描述按需 grep）

当前创新最密集的环节——让压缩从"有损"变成"无损可恢复"。

信息外置是上下文工程的地基环节。没有外置，压缩是不可逆的有损操作，检索恢复无从谈起，清理就是直接丢数据。外置让"有损"变成"无损可恢复"，是整个范式从"塞满窗口"转向"按需拉取"的关键支点：

- **压缩的安全性依赖外置**——没有外置，压缩不可逆；有了外置，压缩变成可逆的中间状态（窗口里是摘要，原始数据在外部可找回）
- **检索恢复的前提是外置**——没有外置，agent 无从检索；有了外置，agent 可自主访问文件系统找回细节
- **清理的容错性依赖外置**——没有外置，清理即永久丢失；有了外置，清理后仍可从外部恢复

反证：Trae 在外置环节做得最弱（无明确的工具结果/历史外置机制），其上下文管理也最薄弱——靠用户重开会话和精简规则文件兜底，没有系统级的上下文生命周期管理。

### 5. 上下文检索 / 恢复（Retrieval）

从外部按需拉回被外置或持久化的信息。

- Agent 用 `read_file` / `grep` / `tail` 读取外置文件
- 向量检索召回长期记忆
- Cursor 的 `@Past Chats` 引用历史对话

关键区别：传统 RAG 是"系统决定召回什么"，Agent 层的检索是"Agent 自己决定拉取什么"。

### 6. 上下文清理 / 驱逐（Eviction）

主动移除不再需要的信息。

- 任务完成后 `/clear`（Anthropic 官方建议第一条）
- 滑动窗口丢弃旧消息

和压缩的区别：压缩是"缩减但保留语义"，清理是"直接移除"。

### 7. 上下文路由（Routing）

不同任务阶段用不同上下文。

- 任务边界切换时清理旧上下文、注入新上下文
- 子 Agent 隔离：大输出任务交给子 Agent，主对话不超载（Claude Code、Deep Agents）
- Codex CLI 的 `/fork` 派生会话：带着已有背景去试另一种方案，主线程不受影响

### 8. 上下文持久化（Persistence）

跨会话保留信息，目的是下次会话还能用。

- 长期记忆（用户偏好、项目状态）
- 状态快照（断点恢复）
- 项目规则文件（`AGENTS.md`、`CLAUDE.md`、`user_profile.md`）

和外置的区别：外置是会话内腾窗口空间（把信息移到磁盘，窗口内留引用），持久化是跨会话保留（这次会话结束了下次还得用）。两者都会写磁盘，但目的和生命周期不同。

### 9. 自主上下文管理（Autonomous Management）

Agent 自己决定何时压缩、何时拉取、何时清理，而非由 harness 按固定阈值触发。

- Deep Agents：给 agent 一个 `compact` 工具，模型在任务边界、消耗大量上下文后等时机自主调用
- Cursor：让 agent 自己决定何时 grep 历史文件、何时读取外置文件
- 与传统 harness 固定阈值触发的区别：agent 根据任务语义判断"这段上下文还重要吗"，而非机械地按 token 数触发

当前趋势：从"harness 固定规则"转向"agent 自主决策"。

### 环节之间的关系

```
注入 → [工具输出截断] → 组装进窗口 → [满了？] → 外置/压缩 → [需要细节？] → 检索恢复
                                      ↓
                                [任务完成？] → 清理 → [跨会话？] → 持久化
```

截断发生在信息进入窗口之前；压缩在窗口满了之后才触发。压缩只是"满了"这条路径上的一个选项，且越来越多地被"外置 + 按需拉取"替代。

### 三个核心环节

九个环节中最重要的三个：

1. **信息外置（地基）**——没有外置，压缩不可逆、检索无从谈起、清理不可容错。是整个范式从"塞满窗口"转向"按需拉取"的支点
2. **上下文压缩（核心问题）**——所有产品都有，是上下文窗口有限这一物理约束的直接应对。有了外置后，压缩从"终点"变成"中间状态"，从不可逆变成可恢复
3. **稳定上下文注入+重注入（安全保障）**——所有产品都做了压缩后重注入项目规则文件。没有这一步，压缩会丢掉关键约束（项目规范、安全边界、用户偏好），agent 在压缩后可能行为偏移

三者形成最小闭环：

```
注入稳定上下文 → 工作 → 满了 → 外置+压缩 → 重注入稳定上下文 → 继续
```

注入保证关键约束在窗口里，压缩+外置处理窗口满了的问题，重注入保证压缩后关键约束不丢。

其余环节重要性低一档：持久化属于跨会话层面，不在会话内闭环中；检索恢复是最前沿方向但当前还没普及为共性；截断、清理、路由、自主管理是优化项，缺了不会让系统崩。

## 三、上下文压缩的定位

上下文压缩是上下文工程的一个子集——当信息超出窗口时的缩减手段。它解决的是"信息太多怎么办"，而上下文工程解决的是"该有什么、什么时候有、怎么有"。

当前趋势：当 Agent 具备工具调用能力后，压缩可以被"外置 + 按需读取"替代（如 Cursor 的文件化按需拉取、LangChain Deep Agents 的虚拟文件系统）。理想状态是上下文里只有当前任务直接需要的信息，不需要的东西一开始就不放入。

## 四、主流 Agent/IDE 实现对比

### Claude Code —— 五层压缩流水线 + 五层记忆金字塔

压缩不是单一策略，而是一条从廉价到昂贵的分层流水线，在每次调用模型前运行。

**压缩流水线（五层，顺序触发）**

| 层级 | 名称 | 做什么 | 触发条件 |
|------|------|--------|----------|
| 1 | Budget Reduction | 对每条消息的工具输出设大小上限 | 每次工具调用时 |
| 2 | Snip | 裁剪较早的历史段落 | 上下文超阈值 |
| 3 | Microcompact | 基于时间衰减做局部压缩，保留 tool_use/tool_result 关联结构 | 上下文继续超阈值 |
| 4 | Context Collapse | 不修改底层存储，生成只读投影给模型看 | 更高压力 |
| 5 | Auto-compact | 调用 LLM 做完整摘要 | 前四层不够时 |

另有 Reactive Compact——当 API 返回 `context_length_exceeded` 时触发的紧急降级，做比 auto-compact 更激进的摘要。auto-compact 触发阈值约为 83.5% 窗口（200K 窗口减去约 33K buffer）。

压缩后触发 `SessionStart('compact')`，重新注入 `CLAUDE.md`、项目规则和 Hook additional context。原始消息仍保留在 JSONL transcript 中，不从磁盘删除。

**记忆系统（五层金字塔）**

| 层级 | 内容 | 加载策略 |
|------|------|----------|
| L1 系统级 | Agent 行为规则、工具 schema、安全约束 | 强制全量加载，常驻 |
| L2 项目级 | `CLAUDE.md`（支持多级作用域） | 启动时加载，压缩后重新注入 |
| L3 持久化记忆 | Auto Memory（`~/.claude/projects/.../memory/*.md`） | 四类：user/feedback/project/reference |
| L4 记忆索引 | `MEMORY.md`（只存指针+摘要，限 200 行/25KB） | 每次会话自动加载 |
| L5 会话级 | 当前任务列表、执行计划、中间状态 | 内存中，结束清空 |

### Cursor —— 动态上下文发现（Dynamic Context Discovery）

范式转移：从"把所有上下文塞进窗口"到"让 agent 按需拉取"。核心是文件作为上下文原语。

| 场景 | 旧模式 | Cursor 做法 | 效果 |
|------|--------|-----------|------|
| 长工具响应 | JSON 全量塞入 | 写入文件，agent 用 `tail`/`read` 按需读 | 减少 summarization 触发 |
| 聊天历史 | 压缩后有损不可逆 | 压缩后给 agent 历史文件引用，可 `grep` 恢复 | 摘要有损但可恢复 |
| Skills | 全文常驻系统提示 | 只放名称+描述，按需加载 `SKILL.md` | 渐进式披露 |
| MCP 工具 | 所有工具描述塞入 prompt | 只塞工具名列表，描述同步到文件夹按需 grep | token 降 46.9% |
| 终端输出 | 手动 copy/paste | 同步到文件系统，agent 直接 `grep` | 与 CLI agent 上下文来源一致 |

### OpenAI Codex CLI —— 双路径压缩 + 任务交接摘要

开源（Rust 实现），上下文管理代码在 `codex-rs/core/src/`。

**双路径压缩**

| 路径 | 机制 | 适用 |
|------|------|------|
| 远程压缩 | 调用 OpenAI `/responses/compact` 端点，服务端返回加密摘要 | 仅 OpenAI 自家模型 |
| 本地压缩 | 客户端用 LLM 生成摘要（`templates/compact/prompt.md`） | 所有模型提供商 |

压缩 prompt：`"You are performing a CONTEXT CHECKPOINT COMPACTION. Create a handoff summary..."`，摘要结构包含：进度/决策、约束/偏好、剩余工作、关键数据。

压缩后保留所有 user 消息原样，重注入上下文设置（mid-turn 压缩时），保留 ghost snapshots 供 `/undo`。触发阈值默认 95% 窗口。工具输出在记录时即截断（默认 10,000 bytes）。跨会话靠用户维护 `HANDOFF.md` 交接文档，支持 `@` 引用跨对话上下文，`/fork` 派生会话做上下文隔离。

### LangChain Deep Agents —— 三级压缩 + 自主压缩

最干净的分层架构，三级按压力递增触发，加一个让 agent 自己决定的工具。

| 级别 | 触发条件 | 做法 | 可恢复性 |
|------|----------|------|----------|
| 大工具结果外置 | 工具响应 >20K token | 写入虚拟文件系统，替换为路径+前10行预览 | agent 可 `read_file` 找回 |
| 大工具输入外置 | 上下文 >85% 窗口 | 截断旧的 write/edit 工具调用，替换为文件指针 | 文件已在磁盘，无损 |
| 摘要压缩 | 外置后空间仍不够 | LLM 生成结构化摘要（含 session intent、artifacts、next steps）；原始消息写入文件系统 | agent 可 `read_file` 找回 |

自主压缩（Autonomous Context Compression）：给 agent 一个 `compact` 工具，让模型自己决定何时压缩。适合压缩的时机——任务边界、消耗大量上下文后获得结论时、即将开始复杂多步操作前、新需求推翻旧上下文时。

### Trae IDE —— 双轨记忆 + 轻量上下文管理

| 类型 | 生效范围 | 存储位置 |
|------|---------|---------|
| 全局记忆 | 所有项目 | `~/.trae-cn/memory/user_profile.md` |
| 项目记忆 | 当前项目 | `~/.trae-cn/memory/projects/{path}/project_memory.md` |

记忆以 Markdown 文件存储，AI 可自动创建/更新/删除。临时指令、模糊偏好、敏感信息不会被保存。其他机制包括 AI 模型按需加载（不常驻内存）、Builder 模式分解大项目为小任务、精简规则文件、控制 MCP 开启数量。

### 跨产品对比

| 维度 | Claude Code | Cursor | Codex CLI | Deep Agents | Trae |
|------|------------|--------|-----------|-------------|------|
| 压缩层数 | 5 层流水线 | 不压缩，外置+按需拉取 | 双路径+截断 | 三级+自主 | 轻量压缩 |
| 外置策略 | 工具结果落盘 | 万物皆文件 | 工具输出截断 | 虚拟文件系统 | 模型按需加载 |
| 可恢复性 | transcript 保留 | 历史文件可 grep | ghost snapshots | 文件系统保留 | 重开会话 |
| 稳定上下文重注入 | CLAUDE.md 压缩后注入 | Skills 按需加载 | AGENTS.md 重注入 | AGENTS.md 启动加载 | 规则文件加载 |
| 自主决策 | 无（阈值驱动） | agent 自主拉取 | 无（阈值驱动） | agent 自主 compact | AI 自主管理记忆 |
| 跨会话 | Auto Memory | @Past Chats | HANDOFF.md + @引用 | 虚拟文件系统 | project_memory.md |
| 上下文隔离 | 子 Agent（只读权限） | 无显式隔离 | /fork 派生会话 | 子 Agent | Builder 分解任务 |

### 各环节共性分析

| 环节 | 是否共性 | 备注 |
|------|:---:|------|
| 工具输出截断 | 是 | 工具结果进入上下文前即截断（Codex CLI 10K bytes，Claude Code Budget Reduction） |
| 信息外置 | 是 | 所有产品都做了工具结果/历史外置 |
| 分层压缩 | 是 | 都有，但依赖程度差异大——Claude Code 投入最多，Cursor 刻意最少 |
| 稳定上下文注入+重注入 | 是 | 项目规则文件（AGENTS.md/CLAUDE.md）启动时注入，压缩后重新注入 |
| 原始数据可恢复 | 是 | 原始数据始终在磁盘可找回 |
| 检索恢复 | 部分 | 只有 Cursor 和 Deep Agents 做到 agent 运行时自主检索；其他是用户触发或会话恢复 |
| 清理 | 是 | 多数靠用户主动 `/clear` 或重开会话，系统自动清理偏粗粒度 |
| 上下文持久化 | 是 | 都有项目规则文件；动态记忆的系统化程度差异大 |

检索恢复是当前唯一还没成为共性的环节——多数产品的"可恢复"指"数据没删，用户/系统可以找回"，而非"agent 运行时自己判断需要、自己去拉取"。

## 五、设计哲学

- 少而精比多而全更好——信噪比优先于信息量
- 让 Agent 自己管理上下文——模型够强时，决策权从 harness 交给 agent
- 压缩是不得已的手段——有更好的上下文管理能力时，压缩角色变小
