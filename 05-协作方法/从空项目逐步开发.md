# 从空项目逐步开发

> 本文档目的：规定从空仓到增量如何使用 AI：讨论、定 v0、实现薄片、按模块加能力或改已有承诺。三类资产与循环见 [`仓库分层与变更循环.md`](./仓库分层与变更循环.md)。

适用：新仓库几乎为空，以及同一仓库上之后的加模块、改已有行为。步骤由人驱动、AI 执行。每个阶段有停标准，未停之前不进入下一阶段。

讨论会话与实现会话分开。实现只读承诺文档和现状；草稿只留在讨论目录。

## 1. 仓库布局

代码出现之前，只建文档目录。`AGENTS.md` 在 v0 能跑之后再写。

```
<project>/
├── AGENTS.md                 # v0 能跑之后：怎么跑、怎么测、禁扩范围
├── CONTEXT.md                # 现状：已做成什么、下一次交付是什么
├── docs/
│   ├── 讨论/                 # 草稿。实现会话不打开
│   ├── v0.md                 # 承诺。实现 v0 时的唯一施工输入
│   └── 模块/                 # 每个模块动手当次才建对应文件
├── src/
└── tests/
```

文档身份：

| 身份 | 路径 | 实现时 |
|------|------|--------|
| 草稿 | `docs/讨论/` | 不打开 |
| 承诺 | `docs/v0.md`、`docs/模块/<名>.md` | 该阶段的施工输入 |
| 现状 | `CONTEXT.md` 与代码 | 以代码为准；承诺按代码回写 |

新建模块则新建 `docs/模块/<名>.md`；改已有行为则改那份已有承诺。项目级承诺始终是 `docs/v0.md`。循环见 [`仓库分层与变更循环.md`](./仓库分层与变更循环.md) 第 1 节。

## 2. 阶段总览

| 阶段 | 会话类型 | 停的标准 |
|------|----------|----------|
| 讨论 | 讨论 | 能填满 `docs/v0.md` 全部字段，且「不做」写得清 |
| 定 v0 | 讨论收口 | 人已审过 `docs/v0.md`；讨论稿已放进 `docs/讨论/` |
| 实现 v0 | 实现 | 主路径能跑；有一条验收命令实际跑过；`AGENTS.md` 与 `CONTEXT.md` 已按代码写好 |
| 完善或改模块 | 先规格、后实现 | 该模块测试绿灯；模块规格已按代码回写；`CONTEXT.md` 已更新下一次交付 |

同一时刻只处在一个阶段。实现会话结束就提交并关掉窗口，下一次交付新开。

---

## 3. 阶段：讨论

目标：收敛做什么、不做什么、先做哪一次交付。本阶段不写代码、不建模块规格、不锁目录树。

### 3.1 建仓

```text
git init
mkdir -p docs/讨论 docs/模块 src tests
```

开一个**讨论**会话。把下面整段发给 AI。

```text
这是一个空项目。当前需求与方案都未定，本会话只讨论，不写代码、不生成完整目录树、不写模块规格。

请先只问我：要解决谁的什么问题、成功时用户完成的那一件事是什么、明确不做什么、有没有已定的技术约束。
一次只问一组（不超过 5 个问题），等我答完再问下一组。
给出选项时写清互斥关系。在我确认之前，任何结论都标成「猜测」。
```

### 3.2 收到方案时怎么收

AI 若一次抛出完整架构或多份规格，只保留对收敛有用的部分，让它改写成三类清单，写入 `docs/讨论/YYYY-MM-DD-议题.md`：

```markdown
# 讨论：<议题>

## 决定
- （已选边、允许当约束用）

## 猜测
- （未验证，允许推翻）

## 下一次交付
- v0 要做成的那一件事：
- v0 明确不做：
```

「决定」以外的长文留在同一文件后部，或留在对话里不入库。

### 3.3 停

能用一句话说出：谁、做哪一件事算成功、v0 不做哪些。说不清就继续 3.1 的追问，不进入第 4 节。

---

## 4. 阶段：定 v0

目标：把「下一次交付」写成唯一承诺文件。全系统模块清单仍不算承诺。

### 4.1 生成 `docs/v0.md`

新开或接着讨论会话，只发这一段（把讨论稿路径换成实际文件）：

```text
根据 docs/讨论/ 里已标为「决定」的条目，写一份 docs/v0.md。只规格化这一次交付，不规格化全系统。
猜测写进文末「以后可能」，正文当中不出现。按下面字段写，缺一项就先问我，不要自行补全。
```

字段必须齐：

```markdown
# v0

## 一句话
<给谁><做成哪一件事>

## 主路径
用户从进入到完成，逐步发生什么（一条路径）。

## 做成的标准
- 怎样启动
- 用户怎样操作一遍
- 哪条命令必须跑过（没有测试时，写启动后能看到的可观察结果）

## 明确不做
- （至少 3 条。写具体能力，不写空话）

## 当前技术栈
- 语言 / 框架 / 运行方式（写「当前采用」，不写「永久」）

## 最小结构
撑住主路径需要哪些部分。每部分用一句话说明职责。不预先展开未做模块的接口。

## 以后可能
（猜测。实现会话不读本节。）
```

### 4.2 人审

对照检查，有一条不通过就改文档、不开始写代码：

- 主路径只有一条，能在 5 分钟内走完演示
- 「明确不做」能拦住至少一个 AI 会顺手做的功能
- 「最小结构」里没有「为以后预留」的空层
- 「以后可能」与正文分开

审过之后：讨论文件全部只存在 `docs/讨论/`。实现用的输入只有 `docs/v0.md`（读到「以后可能」之前）。

---

## 5. 阶段：实现 v0

新开**实现**会话。本会话打开：`docs/v0.md`（正文）、空的或将要写的 `CONTEXT.md`。不打开 `docs/讨论/`，不打开「以后可能」。

### 5.1 开场

```text
这是实现会话。唯一施工文件是 docs/v0.md 的正文（到「以后可能」之前）。
任务：做出主路径能跑的薄片。
约束：
- 只实现主路径和「做成的标准」里的项
- 「明确不做」里的能力本会话不建
- 不添加 v0.md 未写的抽象层、配置项、目录
- 做完先跑「做成的标准」里的命令，再改文档
先列出将创建的文件清单和验收命令，等我确认后再改文件。
```

人只批一件事：清单是否在 v0 范围内。超出就删掉再实现。

### 5.2 做完代码后立刻写的两份文件

**`AGENTS.md`**（短；命令换成项目里真实的）：

```markdown
# AGENTS.md

<v0 一句话定位>。本文件是 AI 代理接手任务前的入口。

## 启动协议

接到任何任务前，按顺序读取：

1. CONTEXT.md —— 已做成什么、下一次交付是什么
2. 实现当前这次交付时读对应承诺：v0 读 docs/v0.md 正文；模块读 docs/模块/<名>.md
3. 先读将改模块的现有代码，再改

## 必备命令

- <install>
- <dev>
- <test>
- <lint>

## 边界

**必做**
- 提交前跑 <test> 和 <lint>
- 规格与代码冲突时，按代码回写承诺文档，并更新 CONTEXT.md

**先问**
- 超出 CONTEXT.md「下一次交付」的范围
- 新建子目录或引入新依赖

**永不做**
- 打开 docs/讨论/ 作为实现依据
- 实现「明确不做」或承诺文末「以后可能」中的项
- 为让测试变绿而删除测试

## 踩坑记录

（随迭代补充。同一类错误出现第二次时在此加一条短规则。）
```

**`CONTEXT.md`**：

```markdown
# CONTEXT.md

## 现在有什么
- 主路径：<实际能走通的步骤>
- 代码入口：<路径>
- 验收命令：<已跑过的命令>

## 下一次交付
- 模块：<名称>
- 要做成：<一件事>
- 仍不做：<从 v0「明确不做」继承、尚未撤销的>

## 当前进度
| 日期 | 阶段结果 |
|------|----------|
| YYYY-MM-DD | v0 主路径能跑 |
```

然后按**实际代码**改 `docs/v0.md`：没做的从正文删掉或移入「以后可能」；做成的标准改成真实命令。

### 5.3 停

- 「做成的标准」里的命令已在本机跑过
- `CONTEXT.md` 的「现在有什么」能对照到文件
- 一次提交，关掉会话

---

## 6. 阶段：按模块完善

一次只做一个模块。加新能力和改已有能力都是：一次规格会话 + 一次实现会话（也可同一窗口先规格、人批后再实现，但实现开始后不再扩规格）。

### 6.1 写模块规格

新建模块规格用本节；改已有承诺见 6.3。

新开会话。打开：`CONTEXT.md`、将改到的现有代码、`docs/v0.md` 的「明确不做」。不打开 `docs/讨论/`。

```text
根据 CONTEXT.md 的「下一次交付」和相关现有代码，写 docs/模块/<模块名>.md。
只规格化这一模块。按模板写，缺信息先问我。写完停，等我确认后再改代码。
```

```markdown
# 模块：<名>

## 要做成
<这一次交付用户或系统多出的能力，一件事>

## 可改文件
- 已存在：
- 将新建：

## 不可改
- （路径或目录）

## 接口与行为
<输入、输出、失败时怎样。只写本模块需要的>

## 验收
- 命令：
- 命令通过时必须为真的行为：

## 不做
- <本模块顺手会做、但这次不做的>
```

人审：可改文件是否够窄；验收命令是否能红能绿；「不做」是否拦住了扩散。

### 6.2 实现

人确认规格后，同一窗口或新窗口：

```text
这是实现会话。施工文件是 docs/模块/<名>.md。
只改「可改文件」，跑通「验收」命令。
验收通过后：按代码回写该规格；更新 CONTEXT.md 的「现在有什么」和「下一次交付」。
不要开始下一个模块。
```

验收命令必须实际跑过。测试变绿的途径是改实现或补合法用例，保持测试数量不因「做完」而减少。

### 6.3 改已有承诺

改已经落地的行为时，打开已有的 `docs/模块/<名>.md`（仍属 v0 主路径的改 `docs/v0.md`），按 6.1 的模板改「要做成 / 可改文件 / 接口与行为 / 验收 / 不做」，人审过后再按 6.2 实现并回写。

### 6.4 同一类错误出现第二次

按这个顺序固化，只选一处为主：

1. 补一条会失败的测试（行为可执行）
2. 改类型或结构，使错误写法编不过
3. 在 `AGENTS.md`「踩坑记录」加一条短规则（仅当 1、2 表达不了）

### 6.5 停本模块、开下一模块

提交 → 关掉会话 → 下一模块回到 6.1。`CONTEXT.md`「下一次交付」每次只保留即将动手的那一项。

---

## 7. 各阶段发给 AI 的检查句

讨论结束前：

```text
列出：决定 / 猜测 / 下一次交付。猜测不得写入 v0 正文。
```

v0 实现结束前：

```text
对照 docs/v0.md：列出本次新建的每个文件属于主路径哪一步；列出未写进 v0 却建了的文件（有则删掉）；跑验收命令并贴结果。
```

模块实现结束前：

```text
对照规格贴出：改动文件是否全在「可改文件」内；验收命令全文输出；CONTEXT.md 下一次交付是否已换成再下一件（尚未实现的那件）。
```

## 8. 本操作硬约束

- 实现会话以承诺文档和 `CONTEXT.md` 为输入；`docs/讨论/` 不当施工依据
- 一个实现会话只完成当前这次交付；下一模块新开
- 禁止为变绿而删测试
