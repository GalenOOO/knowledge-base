# 仓库分层与变更循环

> 本文档目的：规定用 AI 开发时仓库里三类资产是什么、一次交付怎么走、承诺与代码如何对齐。

一次交付：只做成一件可验收的事，范围写在承诺里，做完就提交。空仓到增量共用这一套。分阶段步骤见 [`从空项目逐步开发.md`](./从空项目逐步开发.md)。

## 1. 同一循环

每一次交付：

```text
更新承诺 → 人批 → 实现 → 按代码回写承诺，并更新现状
```

加新能力、改已有行为、空仓第一次交付，都走这一循环。实现中发现承诺写错了：改那份承诺（或改代码使与承诺一致），同一会话内对齐后继续。

讨论可以不上盘。一旦要动手，施工输入是当前承诺。

## 2. 三类资产

| 层 | 回答 | 加载方式 |
|---|---|---|
| 指令 | 每会话怎么干活 | 每会话自动读，必须短 |
| 承诺 | 这一次交付做成什么样；项目级稳定事实 | 实现这次交付时读对应文件 |
| 现状 | 已经做成了什么、下一次交付是什么 | 每会话先读进度；代码与测试为已落地事实 |

指令不管设计正文。承诺不写本周进度。进度不写进长期方案。

### 2.1 指令

写会改变 Agent 行为、且几乎每会话都生效的短规则：

- 一句话定位与技术栈
- 安装 / 开发 / 测试 / lint 命令
- 先读哪几份文件（进度、当前承诺、将改模块的代码）
- 完成定义：验收命令跑过；承诺、代码、进度同一会话对齐
- 先问与永不做：新依赖、改目录、提交密钥、为变绿删测试

常见落点：根目录 `AGENTS.md`（或工具要求的 `CLAUDE.md`，内容与 `AGENTS.md` 同一份）。Monorepo 在子包再放一份，只写该包命令与禁区。细节用链接指向承诺，不把模块设计写进指令文件。

有真实命令之后写齐。讨论阶段若已有该文件，只保留本阶段会话规则。

### 2.2 承诺

分两块，都是施工输入：

**项目级稳定事实**（薄）：给谁、做成哪一类事、明确不做、当前技术栈。只在变更这些事实时改。

**这一次交付**（动手当次才写或才改）：要做成的一件事、可改文件、接口与行为、验收命令、这次不做。只规格化当前这次交付，不预先展开未做模块的接口。

常见落点：`docs/v0.md` 与 `docs/模块/<名>.md`；或 `specs/<feature>/spec.md` 加 `plan.md` / `tasks.md`。改已有行为时打开已有那份承诺，改完人批再实现。

草稿（讨论纪要、被否选项）与承诺分开存放。实现会话以承诺为输入。

### 2.3 现状

- **代码与测试**：已落地行为。验收命令必须实际跑过。
- **进度**：现在有什么、下一次交付是哪一件、仍不做哪些。下一次交付只保留即将动手的一项。

常见落点：`CONTEXT.md`；或写在这一次交付的 `plan.md` / `tasks.md` 勾选里。进度随每次交付更新。

## 3. 承诺与代码如何对齐

| 时刻 | 谁是输入 | 做什么 |
|---|---|---|
| 实现开始前 | 当前承诺 | 人批范围后再改代码 |
| 实现结束后 | 代码（含已跑过的验收） | 按代码回写承诺，更新进度 |

同一事实只住一份承诺。改行为时：改拥有该事实的那份承诺、改代码、跑验收、更新进度，同一会话做完。

行为对错由验收命令与测试判定。承诺是施工与对齐用的文本，不替代门禁。

## 4. 空仓时

代码出现前只建文档目录。第一次交付的项目级稳定事实与「做成哪一件事」写在同一份承诺里，能跑之后再补指令里的真实命令。之后每加一个模块或改一处已有行为，仍走第 1 节循环。目录与阶段步骤见 [`从空项目逐步开发.md`](./从空项目逐步开发.md)。

## 5. 硬约束

- 实现开始前以当前承诺为施工输入
- 实现结束后以代码为现状，回写承诺并更新进度
- 一个实现会话只完成当前这次交付
- 禁止为变绿而删测试
